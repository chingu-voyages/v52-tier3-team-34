## Overview

This document outlines the implementation plan for the Live Music Finder API, following the "Contract First, Implementation Later" strategy. It combines requirements from Task #63 (Multi-Environment Testing Infrastructure) and API Standardization needs.

### Key Principles
1. Establish all API contracts before implementation
2. No breaking changes after next PR
3. Support for multiple deployment environments
4. Comprehensive testing infrastructure
5. Clear path for future enhancements

### Strategic Approach
- **Contract First**: Define all API interfaces upfront
- **Implementation Later**: Create atomic issues for feature implementation
- **Testing Focus**: Ensure robust testing across environments
- **Documentation**: Maintain clear, up-to-date documentation

## Resource Definitions

### 1. Users Resource

#### Current Scope
- Basic user management without authentication
- Google authentication to be implemented in future phase
- Focus on user profile and relationships

#### Data Structure
```typescript
interface User {
  id: string
  email: string
  name: string
  // OAuth-ready fields (optional)
  authProvider?: 'local' | 'google';  // extensible for more providers
  providerId?: string;                // stores OAuth provider IDs
  googleId?: string
  profileImage?: string
  createdAt: string
  updatedAt: string
  venues?: Venue[]    // Owned venues
  events?: Event[]    // Created events
}
```

#### Endpoints
```typescript
// List users
GET /api/v1/users
?page=1&limit=20
?orderBy=name&order=desc
?fields=id,name,email

// Get single user
GET /api/v1/users/:id
?fields=id,name,venues
?include=venues,events

// Create user (basic profile)
POST /api/v1/users
{
  email: string
  name: string
  profileImage?: string
}

// Update user
PATCH /api/v1/users/:id
{
  name?: string
  profileImage?: string
}

// Delete user
DELETE /api/v1/users/:id
```

### 2. Events Resource

#### Current Scope
- Full CRUD operations
- Geolocation support
- Zone search functionality
- Venue relationship

#### Data Structure
```typescript
{
  id: number
  title: string
  description: string
  startDate: string      // ISO 8601
  endDate: string        // ISO 8601
  status: "draft" | "published" | "cancelled"
  createdAt: string
  updatedAt: string
  venue: Venue           // Related venue
  createdBy: User        // Event creator
  coordinates: {         // Inherited from venue
    lat: number
    lng: number
  }
}
```

#### Endpoints
```typescript
// List events
GET /api/v1/events
?page=1&limit=20
?status=published
?orderBy=startDate&order=desc
?fields=id,title,startDate
?include=venue

// Get single event
GET /api/v1/events/:id
?fields=id,title,description
?include=venue,createdBy

// Get event in GeoJSON format
GET /api/v1/events/:id/geojson

// Search events in zone
GET /api/v1/events/zone
?lat=40.7128&lng=-74.0060
?radius=10
?startDate=2024-01-01T00:00:00Z
?status=published

// Create event
POST /api/v1/events
{
  title: string
  description: string
  startDate: string
  endDate: string
  status?: "draft" | "published" | "cancelled"
  venueId: number
}

// Update event
PATCH /api/v1/events/:id
{
  title?: string
  description?: string
  startDate?: string
  endDate?: string
  status?: "draft" | "published" | "cancelled"
}

// Delete event
DELETE /api/v1/events/:id
```

### 3. Venues Resource

#### Current Scope
- Full CRUD operations
- Geolocation support
- Contact information
- Image management
- Owner relationship

#### Data Structure
```typescript
{
  id: number
  name: string
  description: string
  address: string
  contact: {
    phone?: string
    email?: string
    website?: string
  }
  images: string[]      // URLs to venue images
  coordinates: {
    lat: number
    lng: number
  }
  createdAt: string
  updatedAt: string
  owner: User           // Venue owner
  events?: Event[]      // Events at this venue

```

#### Endpoints
```typescript
// List venues
GET /api/v1/venues
?page=1&limit=20
?orderBy=name&order=asc
?fields=id,name,address
?include=events

// Get single venue
GET /api/v1/venues/:id
?fields=id,name,description
?include=owner,events

// Get venue in GeoJSON format
GET /api/v1/venues/:id/geojson

// Create venue
POST /api/v1/venues
{
  name: string
  description: string
  address: string
  contact: {
    phone?: string
    email?: string
    website?: string
  }
  images: string[]
  coordinates: {
    lat: number
    lng: number
  }
  userId: number      // Owner ID
}

// Update venue
PATCH /api/v1/venues/:id
{
  name?: string
  description?: string
  address?: string
  contact?: {
    phone?: string
    email?: string
    website?: string
  }
  images?: string[]
  coordinates?: {
    lat: number
    lng: number
  }
}

// Delete venue
DELETE /api/v1/venues/:id
```

### Resource Relationships

```
User
└── venues (owned venues)
└── events (created events)

Venue
└── owner (user)
└── events (events at venue)

Event
└── venue (location)
└── createdBy (user)
```

#### 1.1 URL Structure
- Implement `/api/v1/` versioning
  ```
  /api/v1/events
  /api/v1/venues
  /api/v1/users
  ```
- Reserve `/bulk` endpoints
  ```
  /api/v1/events/bulk
  /api/v1/venues/bulk
  ```
- Standardize query parameter formats
  ```
  ?filter[field]=value
  ?sort=field:direction
  ?fields=id,name,description
  ?include=relation1,relation2
  ```

#### 1.2 Response Structure
```typescript
{
  status: "success" | "error",

  meta?: {

      limit: number,
```

## Authentication Design (OAuth-Ready)

#### Authentication Endpoints Structure
- Separate from Users CRUD operations
- Future endpoints (no breaking changes needed):
  ```
  POST /api/v1/auth/google
  GET  /api/v1/auth/google/callback
  ```

#### Users Resource Schema (OAuth-Ready)
```typescript
interface User {
  id: string;
  email: string;
  name: string;
  // OAuth-ready fields (optional)
  authProvider?: 'local' | 'google';  // extensible for more providers
  providerId?: string;                // stores OAuth provider IDs
  // ... other user fields
}
```

#### Design Benefits
1. **Separation of Concerns**
   - Authentication logic isolated from Users CRUD
   - Clean separation between auth flows and user management

2. **Future-Proof Schema**
   - Optional OAuth fields don't affect current operations
   - Extensible for additional authentication providers
   - No schema migrations needed for Google Auth implementation

3. **Backward Compatibility**
   - Existing endpoints remain unchanged
   - Current implementations continue working
   - New auth features can be added incrementally
